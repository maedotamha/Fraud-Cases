Fraudulent transactions are rare, sneaky, and expensive. In this first phase of Adey Innovations' fraud detection system, I analyzed 434,000 real-world transactions across two completely different data domains — and found signals so strong they could catch fraud before a single model is trained.

The Problem: Why Fraud Detection Is Genuinely Hard

Fraud detection sits at the intersection of two painful trade-offs. False positives — flagging a legitimate purchase as fraud — frustrate real customers and erode trust. False negatives — missing actual fraud — cause direct financial loss. Getting the balance right requires more than a good model. It requires understanding the data deeply enough to build features that speak directly to how fraudsters actually behave.

At Adey Innovations, we're building a unified detection capability across two very different transaction streams:

  • E-commerce transactions with rich behavioral context — device IDs, signup times, IP addresses, browser fingerprints
  • Bank credit card transactions where features are anonymized via PCA for regulatory compliance

This report covers Phase 1: understanding both datasets, engineering features that capture how fraud actually manifests, and preparing our training sets correctly.

The Datasets: Two Very Different Imbalance Problems

151,112 E-commerce transactions
9.36% E-commerce fraud rate
283,726 Credit card transactions

These two datasets have radically different imbalance profiles. At 9.36%, the e-commerce data is moderately imbalanced — a real challenge, but workable. The credit card data, at 0.17%, is a 600:1 ratio. A model that predicts "legitimate" for every single transaction would achieve 99.83% accuracy — while catching exactly zero fraudulent cases. This is precisely why overall accuracy is a useless metric for fraud detection, and why we evaluate on AUC-PR and F1-Score instead.

Part 2 — Geolocation: Turning IP Ranges Into Fraud Signals

The IP-to-country mapping file contains 138,846 IP ranges, not individual addresses. This means a standard table join on exact values will fail — we need a range-based lookup.

The Technique: pd.merge_asof

The approach: convert every IP to a 64-bit integer, sort both tables on the lower bound, and use merge_asof to find the largest lower bound that is still ≤ each transaction's IP. A final bounds-check confirms the IP falls within the matched range. 

# Convert IPs to integers
fraud_df['ip_int'] = fraud_df['ip_address'].astype(np.int64)
ip_df['lower_int'] = ip_df['lower_bound_ip_address'].astype(np.int64)
ip_df['upper_int'] = ip_df['upper_bound_ip_address'].astype(np.int64)

# Range join — O(n log n), no row-by-row iteration
merged = pd.merge_asof(
    fraud_sorted,
    ip_sorted[['lower_int', 'upper_int', 'country']],
    left_on='ip_int', right_on='lower_int',
    direction='backward'
)

# Validate: ip_int must fall within the matched range
merged['country'] = merged.apply(
    lambda r: r['country'] if r['ip_int'] <= r['upper_int'] else 'Unknown', axis=1
)

Part 3 — Feature Engineering: Teaching the Model How Fraud Thinks

Raw fields like signup_time and ip_address are useless directly. What matters is what they imply about the transaction's context. We engineered four families of features:

3.1 time_since_signup — The Single Most Powerful Signal

This feature measures the elapsed hours between account creation and the transaction:

fraud_df['time_since_signup'] = (
    fraud_df['purchase_time'] - fraud_df['signup_time']
).dt.total_seconds() / 3600

The distribution is wide — median ~57 days, but with a long tail toward zero. Segmenting it reveals something extraordinary:

Time Since SignupFraud Rate
< 1 hour99.52% 🚨
1 – 6 hours3.33%
6 – 24 hours4.10%
1 – 7 days4.46%
> 7 days4.57%
Transactions placed within 1 hour of account creation are fraudulent 99.52% of the time. This is not a model prediction — it is a direct observation from the data.

This pattern is consistent with a well-known fraud vector: attackers create throwaway accounts specifically for a one-time fraudulent purchase, then abandon the account. The sub-1-hour window is the telltale signature.

3.2 Transaction Velocity — tx_count_24h

We computed each user's cumulative transaction count up to each purchase. Legitimate users typically shop infrequently. A burst of transactions from a single account in a short window — credential stuffing, account takeover, or automated purchasing bots — is a strong fraud signal.

3.3 Temporal Features

hour_of_day and day_of_week capture fraud patterns tied to operational rhythms: fraud teams have lower coverage at 3am on a Sunday; attackers know this.

Part 5 — The Preprocessing Pipeline

5.1 The Golden Rule: Split Before You Resample

One of the most common and damaging mistakes in fraud detection pipelines is applying oversampling before the train/test split. If SMOTE-generated samples appear in both training and test sets, the model appears to generalize well — but it is essentially memorizing synthetic test data. Every performance metric becomes meaningless.

Our rule: stratified split first, SMOTE second, test set untouched.

5.2 Why SMOTE Over the Alternatives?

MethodMechanismProblem
Random OversamplingDuplicates minority rowsModel memorizes exact rows → overfitting
Random UndersamplingRemoves majority rowsDiscards real legitimate transaction data
SMOTE ✓Interpolates new synthetic minority samplesSlightly slower; our chosen approach

SMOTE works by finding each fraud sample's k-nearest fraud neighbors and generating new synthetic points along the line segments connecting them. The result is a more diverse fraud representation that generalizes better than simple duplication.

Part 6 — Five Findings That Drive the Rest of the Project

Finding 1 — The 1-Hour Rule

Transactions within 1 hour of signup are fraudulent 99.52% of the time. This is the single most actionable insight from the entire dataset — implementable as an immediate rule-based flag with no model required.

Finding 2 — Geographic Concentration

Five countries (Luxembourg, Ecuador, Tunisia, Peru, Bolivia) show fraud rates 3–4× the global average. Country-of-origin is a high-signal, low-cost feature that should be in every model.

Finding 3 — Direct Traffic Anomaly

Direct-channel users commit fraud at 10.54% vs 8.93% for SEO users. Small but consistent — suggests programmatic or automated account creation bypassing referral tracking.

Finding 4 — Card Testing in Credit Card Data

Median fraud amount ($9.82) is far below the legitimate median ($22.00), while mean fraud ($123.87) exceeds the legitimate mean ($88.41). This bimodal pattern is the signature of card-testing behavior.

Finding 5 — PCA Feature Hierarchy

V17, V14, V12, V10 are the dominant fraud signals in the credit card data. SHAP analysis in Phase 3 will decode what these latent components represent in behavioral terms.
